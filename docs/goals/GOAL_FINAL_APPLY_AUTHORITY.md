# Goal final-apply authority contract

Status: Stage 7C.2A authority contract. This document defines authorization for a future exact fast-forward; it does not authorize or implement a Git write. Stage 7C.2B remains responsible for execution and recovery.

## Existing authority

- Goal approvals are persisted in `goal_approvals`, with one existing gate vocabulary and immutable request details. `requestGoalApproval()` creates pending records and `decideGoalApproval()` permits an explicit user approval or a system denial. Decisions are terminal and idempotent when repeated identically.
- `evaluateCompletion()` is the completion authority. For a Goal whose policy requires base application, final acceptance is bound to the current definition version/hash and integration tree. Completion remains false until an `apply_to_base` operation is durably applied at the current integration head, or a separate user approval carries the exact `action: "applied_externally"` attestation.
- `preflightFinalApply()` is the existing read-only Git authority. It checks the recorded base, current branch/HEAD, clean checkout, Goal-ref identity and checkout state, fast-forward ancestry, full changed-path scope, sensitive paths, and complete content scan. Its diff and path displays are bounded/redacted separately from safety checks.
- No final-apply-specific prospective authority currently binds a user approval to one exact source, destination, repository and reviewed change summary. There is no final-apply writer or request endpoint.

## 7C.2A intent

The server constructs `FinalApplyIntent` schema version 1 with action `apply_to_base_intent`. Its authority fields are:

- Goal ID and approved definition version/hash;
- exact Goal ref, full integration commit ID, and integration tree ID;
- registered project/repository identity, full base ref, recorded base branch and expected old base commit;
- SHA-256 digests of the complete changed-path set, bounded diff-stat display, and bounded diff-preview display, plus the preview truncation flag;
- a SHA-256 `intentDigest` over a versioned canonical serialization of all those fields.

Commit/tree IDs retain their full repository-specific width (40 hexadecimal characters for SHA-1, 64 for SHA-256). The client never supplies or replaces authority fields. The stored explanation is bounded to the approval read model's 4,000-character detail limit; the complete path and content safety scans remain independent of that display. The preview digest binds the exact bounded/redacted preview the approval record presents, while the full source commit/tree and complete path-set digest bind the underlying change.

Repository identity is a server-computed SHA-256 over a versioned tuple containing the registered project ID, canonical real repository root, canonical Git common directory, and project-relative scope. This prevents replay to another registered project/repository that happens to use the same branch name. It intentionally treats moving a repository or changing the registered project root as stale authority; it is a local identity, not a portable repository UUID.

Canonical digest input is a version-tagged JSON array in fixed field order, not arbitrary object serialization. No timestamps, formatted prose, or client-provided digest participate. Each authoritative field and preview digest has a sensitivity test proving a changed value changes the digest; identical inputs produce the same lowercase SHA-256 digest.

## Eligibility and revalidation

`prepareFinalApplyIntent(db, goalId)` is read-only. It calls `evaluateCompletion()` and accepts only a non-`ok` evaluation whose sole failure is `final_apply_required`, with required criteria, milestones, findings policy, final review, and final acceptance all satisfied. It also refuses an unapproved or invalid current definition, terminal/manual-reconciliation Goal, active cycle/run, any unresolved planned integration operation, or a policy that does not require base application. It then calls the existing `preflightFinalApply()` and requires `ready_for_approved_apply`; it does not duplicate Git policy.

The persisted approval request uses the existing service with gate `final_apply`, risk `high`, requester `user`, and `action: "apply_to_base_intent"`. Both the existing service and migration insert guard reject prospective intent records with another risk or requester. The immutable detail also records the registered `repositoryProjectId` used to compute the repository identity. No new public request endpoint or UI action is introduced in 7C.2A. The existing decision endpoint routes prospective intent approvals through asynchronous read-only validation before an explicit user approval, then rechecks Goal, definition, source-head, destination and active-work database bindings inside the decision transaction. Git reads occur outside SQLite transactions. A Git ref or repository identity can still change in the interval before the approval decision commits; the approved record remains bound to the earlier snapshot and cannot authorize a different one. 7C.2B must revalidate after acquiring its Git coordination and immediately before the write.

`validateFinalApplyAuthority(db, goalId, approvalId)` is read-only and requires the exact approval to be pending or explicitly approved according to its caller. It validates strict versioned detail shape, Goal/gate/risk/requester/status/decision actor, matching typed digest metadata, canonical digest, current definition/hash, completion prerequisites, current repository identity, source commit/tree, destination branch/base commit, fresh preflight, and absence of active work or unresolved operations. A mismatch returns a specific refusal; it never refreshes or rebinds an approval. The write stage must call it for an approved decision and must use only the returned authority.

## Approval lifecycle and idempotency

- An identical current request returns the existing pending or approved approval. An approved record is never replaced.
- A denied record is returned as denied by default. A new attempt at the same digest is permitted only through a distinct explicit request (`retryDenied: true`); it creates a new approval and leaves the denied record intact. A changed snapshot naturally has a different digest.
- A SQLite `BEGIN IMMEDIATE` request transaction serializes duplicate creation across Master processes. An additive partial unique index permits at most one live pending/approved prospective approval for a Goal/digest. A denied record is excluded so an explicit retry can be recorded.
- When a new, different current intent is requested, older pending prospective intents for that Goal are system-denied with a stale note through the existing decision service. Their history remains. An approved old intent remains immutable, but revalidation refuses it while its authority differs. If a stale pending approval is decided before a replacement request, the existing decision endpoint returns a stale refusal and leaves it pending; a later request settles it. No stale approval is silently selected or rebound.
- Two requests for different snapshots may leave historical approvals for different digests; only the digest matching the current complete evaluation and preflight can validate. Two decisions on one approval retain the existing exactly-once rule: one terminal decision wins, an identical repeat is a no-op, and a conflicting decision is refused.

Final acceptance, prospective Turing apply authority, and `applied_externally` remain distinct. Prospective detail uses only `apply_to_base_intent`; it never uses `applied_externally`. Approving this intent does not create an applied operation, move a ref, complete the Goal, or start/resume it. Completion continues to report `final_apply_required` until a later operation is durably proven or a separate valid external attestation is made outside this stage.

## Stage 7C.2B implementation protocol and recovery contract

The internal writer persists one immutable planned `apply_to_base` operation containing the approval ID, intent digest, source commit/tree/ref, target ref, expected-old commit, and exact authority-check record before the first Git ref write. The order is: validate approved authority; persist the plan; recheck the same complete authority and current checkout/ref state; perform one guarded ref transaction; synchronize the checkout; persist verified applied evidence; reconcile the database record after interruption.

For recovery, the observed destination equal to the expected old commit means no write occurred and may be aborted/retried only after fresh checks. Equality to the approved new Goal commit may be reconciled as applied only when the immutable planned record, approval, digest, source ref, and transaction identity all match. A different or missing/unreadable destination fails closed without a Git write. Mere commit equality without a pre-existing Turing planned record is not proof of a Turing operation; external application remains a separate user attestation.

An ordinary `git merge --ff-only` after a prior read is not an atomic expected-old check. 7C.2B must coordinate at the common Git ref store and use a Git compare-and-swap transaction that verifies the Goal ref is still the approved source and updates the base ref only if it is still the approved expected-old commit. `git update-ref --stdin` supports a transaction containing expected-old `verify` and `update` commands; a failed compare-and-swap performs no base-ref update ([Git documentation](https://git-scm.com/docs/git-update-ref)). The transaction must not create a merge commit, reset, rebase, cherry-pick, or force-update. Any worktree/index refresh is a separate non-destructive concern: it must never overwrite edits made after preflight and must fail safely if it cannot synchronize.

Concurrency expectations:

- Identical request races serialize at SQLite and converge on one live approval. Different snapshots have different digests and only the current one validates.
- Approval-decision races are serialized by the existing terminal decision transaction. A Goal advance, definition amendment, stale review/acceptance, base movement, checkout change, dirty worktree, Goal-ref movement, or safety failure makes the old intent fail revalidation.
- A crash after persisting `planned` but before the Git transaction observes the old ref and aborts/retries only after fresh checks. A crash after the ref transaction but before database reconciliation observes the approved new ref and reconciles only with matching operation provenance. Third-party movement or an unreadable ref is never guessed over.
- The CAS transaction protects the expected-old base ref and approved Goal ref at the write boundary. A process-local mutex or `merge --ff-only` alone is insufficient. SQLite and Git cannot form one atomic transaction; durable planned-operation recovery is required.

### Checkout/index safety design gate and 7C.2B candidate implementation

The supported target is a non-bare, full (non-sparse) registered repository worktree whose canonical root is the registered `git_root`, whose symbolic `HEAD` is the recorded base branch at the recorded base commit, and which is the sole registered worktree with that destination branch checked out. A Goal branch checked out in any linked worktree, a duplicate destination checkout, a detached/wrong checkout, an unresolved index, sparse checkout/index, or a changed worktree registration is refused. Linked worktrees on other branches are allowed only when the source Goal ref is not checked out there. Any base or source commit tree containing a gitlink/submodule is refused because this operation does not recursively synchronize submodule worktrees.

The ref CAS and checkout refresh are separate durable steps. After the atomic `update-ref --stdin` transaction, the active checkout is synchronized with `git read-tree -m -u <expected-old> <approved-new>`. This is Git's documented two-tree fast-forward merge: it updates the index and worktree, refuses tracked conflicts, and does not move a ref, switch branches, force checkout, or discard tracked edits. Pre-implementation experiments found that `read-tree` may overwrite an _ignored_ untracked file at a newly added Goal path. Immediately before sync the writer therefore enumerates all untracked paths, including ignored paths via `git ls-files --others -z`, and rejects exact or file/directory-prefix collisions with any path the Goal will write. That collision scan runs before plan persistence, before CAS, and again immediately before `read-tree`. SHA-1 and SHA-256 tests cover successful synchronization and an ignored collision refusal. A separate characterization test demonstrates that advancing a checked-out ref alone leaves the index/worktree at the old tree and reports staged changes; `read-tree` brings the isolated checkout to the approved `HEAD` with clean status. A tracked edit made after CAS is preserved and leaves the operation incomplete. An unrelated untracked file created after CAS is also preserved, but the apply stays incomplete because the checkout is not clean. An ignored unrelated file present before apply remains present without making Git status dirty.

If sync refuses, status is not clean, the index is locked/unreadable, the branch/worktree registration changes, or any postcondition differs, the ref is not rolled back. The immutable operation remains `planned` with bounded observation metadata in `recovery_json`; the service returns `checkout_index_sync_incomplete` or `manual_reconciliation_required`. Recovery performs no Git writes: it verifies the operation record and unique ref-transaction reflog marker, observes refs and checkout/index state, and marks the operation applied only when all success postconditions are already true. Otherwise it leaves the operation unresolved for explicit manual repair. This prevents a retry from issuing a second ref transaction.

The transaction cannot lock arbitrary editors or external Git processes. The ref CAS serializes competing ref movement; `read-tree` uses Git's index lock and native tracked-file checks; the service rechecks registered worktrees, branch, `HEAD`, index/worktree status, and untracked target collisions immediately before the CAS and immediately before synchronization. It verifies source/destination refs and a clean checkout after sync. An external filesystem edit detected before sync is preserved and leaves the operation incomplete. The remaining narrow race with an external writer that creates an ignored untracked target after the final collision scan but before Git updates that path cannot be eliminated by the ref transaction; this stage does not claim an OS-level lock against unrelated editors. Recovery never attempts a destructive repair.

The synchronization behavior was characterized in disposable repositories before implementation and repeated by the final-apply tests for SHA-1 and SHA-256. The registered-worktree digest omits only Git's per-worktree `HEAD` line, which necessarily changes when the checked-out destination ref advances; it still binds the registered paths, branches, lock/prunable markers, and checkout layout. Git protocol references: [git-update-ref](https://git-scm.com/docs/git-update-ref), [git-read-tree](https://git-scm.com/docs/git-read-tree).

## Durable operation schema

Migration 024 adds only nullable `goal_integration_ops.approval_id`, constrained to `apply_to_base`, and binds the row to an approved high-risk user decision for the exact prospective intent. The immutable operation `checks_json` contains a strict versioned record and digest that bind the approval, repository identity, source ref/head/tree, destination ref/expected-old commit, object format, changed-path digest, and worktree layout. The existing operation identity trigger now keeps `approval_id` immutable. The existing one-planned-operation-per-Goal index serializes unresolved work; a second partial unique index permits only one planned/applied row per approval while allowing a new historical attempt after a proven abort. An applied transition requires bounded recovery proof fields. Historical Goal operations and approvals remain unchanged.

The service accepts only `{ goalId, approvalId }`; it accepts no source or destination refs/commits from its caller. It returns explicit machine outcomes: `applied`, `already_applied`, `refused`, `concurrent_ref_conflict`, `git_operation_failed`, `checkout_index_sync_incomplete`, or `manual_reconciliation_required`. Ref equality alone never returns success. A completed identical approval is reverified from its immutable record, approval, repository identity, source tree, exact reflog marker, and checkout proof, then returned as `already_applied` without another Git write.

Recovery is observation-only. With destination still at expected-old and no exact operation reflog marker, it aborts the planned row. With the approved new commit and the unique marker, it marks applied only after independently checking the source ref, repository identity, registered checkout, branch, `HEAD`, index, worktree, untracked-path collisions, and clean status. A third value, changed source, missing marker, malformed record, or incomplete checkout stays unresolved or requires manual reconciliation. Recovery never runs `update-ref`, `read-tree`, reset, checkout, or another Git write. `evaluateCompletion()` no longer trusts an `applied` row alone; it checks the exact approval, immutable operation digest, recovery proof, repository/tree identity, and reflog evidence. Prospective approval alone still leaves completion at `final_apply_required`.

## Stage 7C.2B.2 ref-only architecture decision

Stage 7C.2B.1 is accepted as a **blocked evidence checkpoint**, not a successful safety remediation. Its ignored-file overwrite proves that the checked-out-worktree synchronization contract cannot currently guarantee preservation against arbitrary concurrent filesystem writers. The detailed Stage 7C.2B.2 investigation and proof matrix are in [GOAL_FINAL_APPLY_REF_ONLY_DECISION.md](../history/goals/GOAL_FINAL_APPLY_REF_ONLY_DECISION.md).

Stage 7C.2B.2 selects **manual handoff as the V1 boundary**. A ref-only update to the recorded base is not safe under arbitrary concurrent Git clients: `git worktree list --porcelain -z` is only a snapshot, and a linked checkout can appear before low-level `git update-ref` CAS. The deterministic Linux characterization shows the CAS succeeds while the newly checked-out branch's symbolic `HEAD` resolves to the new commit and its index/files remain at the old tree. An independent create-only delivery-ref characterization also shows that an unborn linked worktree can name a proposed delivery ref before it exists; creating the ref changes what its symbolic `HEAD` resolves to without updating its index. Neither low-level ref transaction atomically guards worktree occupancy.

Accordingly, the accepted 7C.2A version-1 `apply_to_base_intent` retains its original meaning and must not authorize a delivery-ref update or manual-handoff operation. Existing approvals remain audit history; pending old intents should be system-denied with an auditable supersession reason when a new contract is implemented, while approved records remain immutable and are rejected by any new mode-specific validator. Historical operation rows and proofs must never be replayed or reinterpreted. No migration 025 is implemented here.

For a manual handoff, Turing makes no Git ref, `HEAD`, index, or worktree change. A future versioned handoff record should bind the accepted Goal/definition, repository identity, exact Goal source ref/commit/tree, observed target base ref/commit/tree, reviewed-change digest, bounded preview identity, evidence and review identities, and its own canonical digest. This record is not an operation approval. A new “ready for manual integration” concept may describe a prepared result, but it does not satisfy current `applyToBase: "required"` completion. `evaluateCompletion()` remains unchanged; a distinct user-only `applied_externally` attestation can remain a separate later path and represents the user's assertion, not Turing-observed application.

No production final-apply writer, endpoint, UI action, migration, provider call, subscription use, or completion change is part of this design stage. `applyApprovedGoalToBase()` remains quarantined and unreachable from production routes, agents, schedulers, and UI. Production continues to use `DisabledGoalExecutor`. Do not begin 7C.3 before independent review of the pushed evidence checkpoint.

## Stage 7C.2B.1 non-destructive checkout remediation — blocked

Independent safety review rejected candidate `b544ff1a7a4251b4a5bd982d08a7dc70e2927927` because a user file can be overwritten after the final collision scan. A new full-authority regression in `src/server/goals/finalApply.test.ts` uses a temporary Git/SQLite fixture and a test-local Git executable wrapper. The wrapper injects `src/final-apply.txt` after `assertReadyForCheckoutSync()` and the final `hasUntrackedTargetCollision()` return, immediately before invoking the real `git read-tree -m -u`. It records the original bytes `USER-ORIGINAL-IGNORED-BYTES\n`; the path is ignored through `.git/info/exclude`. The wrapper observed `git status --porcelain` as `D  src/final-apply.txt` after CAS but before checkout sync. Git exited 0, replaced the file with `approved Goal content\n`, and the service returned `applied`; the resulting checkout was clean and completion reported `applied_by_turing`. This reproduction also passed from a detached worktree at the exact rejected candidate SHA with only the test overlaid. The earlier scans miss this because the filesystem mutation occurs after the last scan; a clean postcondition cannot reveal bytes already overwritten.

Additional disposable filesystem/Git characterization in `src/server/goals/finalApplyFilesystemCharacterization.test.ts` ran on Linux 6.8, Git 2.43.0, Node 22.23.1, uid 1000. Ordinary untracked targets, symlinks at a new target, a parent replaced by a symlink, tracked edits, staged index edits, index-lock contention, and file/directory transitions with user children were refused by `read-tree` and their checked bytes/targets remained. A read-only directory caused `read-tree` to fail after it had already created a lexically earlier Goal file, demonstrating a partially updated checkout. The ignored-target case above is different: Git overwrites it and exits successfully. These observations characterize this Linux/Git version only; no Windows run establishes equivalent protection.

### Architecture decision

**Decision: block the checked-out-branch writer. No safe replacement has been established under the current contract.**

- **A — stronger checks on the live checkout: rejected.** More scans, process mutexes, watchers, or post-checks leave a time-of-check/time-of-use interval. `O_EXCL`-style creation would not conditionally protect all tracked replacements, symlinks, directory transitions, and arbitrary writers.
- **B — stage a complete checkout elsewhere: rejected as a standalone fix.** The final multi-path transfer into the live checkout still has the same replacement race. Swapping a whole directory would displace the user's live tree, unrelated files, open handles, and concurrent edits; rollback is not a safe data-preservation guarantee.
- **C — Git-native checkout: rejected for this guarantee.** The exact `read-tree -m -u` path demonstrably overwrote an ignored target and can partially update before a later error. This evidence does not prove safe concurrent filesystem semantics for `checkout`, `switch`, or `checkout-index` on both target platforms.
- **D — narrower ref-only architecture: recommended for separate design review, not implemented.** Consider CAS-updating the approved destination ref only when it is not checked out in any worktree, leaving checkout to a later explicit user operation. This changes preflight/intent binding and what completion means; existing approvals must not be silently rebound to it.

No migration 025 or production writer changes were made. The existing SQLite planned-operation and recovery model remains necessary, but cannot recover bytes already overwritten by the candidate algorithm. Linux and Windows checked-out live-worktree application are therefore not safety-qualified. Production final apply remains unreachable and `DisabledGoalExecutor` remains in use. Stage 7C.2B.1 is blocked pending independent review of the narrower architecture; 7C.3 must not begin.

## Stage 7C.2B.3 immutable manual handoff implementation candidate

Stage 7C.2B.2 selected manual integration as the V1 boundary. Stage 7C.2B.3 implements that decision as an internal-only service, pending independent review. The historical 7C.2A prospective approval and rejected 7C.2B writer retain their original meanings.

- `buildManualHandoffSnapshot()` uses `evaluateCompletion()` and only proceeds when its single failure remains `final_apply_required`; the current approved definition, actual user acceptance row, passing independent final review, evaluator-selected evidence, current Goal ref, recorded base ref, fast-forward ancestry, full changed paths, and complete relevant content scan are bound.
- `prepareManualHandoff()` persists one canonical v1 record in SQLite migration 025. Equal content digests are deduplicated transactionally. Payload, approval/review links, source/base IDs and digest are immutable. A changed snapshot creates a new record.
- `validateManualHandoff()` and `getManualHandoffProjection()` are read-only. They rebuild the current snapshot and report current/stale/unavailable/invalid without updating historical payloads. The bounded display gives only read-only `git show`/`git diff` commands and clearly says Turing did not apply the result.
- The service does not use `preflightFinalApply()`, modify refs/HEAD/index/worktree/config/metadata, create approvals, add `goal_integration_ops`, attest external application, transition Goal state, or call providers. There is no new route, button, scheduler, or automatic publication.
- Completion remains strict: a handoff does not change `finalApply.ok`, does not remove `final_apply_required`, and does not complete the Goal. Production still constructs `DisabledGoalExecutor`; the rejected `applyApprovedGoalToBase()` remains quarantined.
- SQLite snapshot rechecks and fresh retrieval reduce stale presentation; they cannot reserve repository state from external Git processes. Linux SHA-1/SHA-256 characterization uses disposable repositories. Windows behavior is unverified.

The contract is in [GOAL_MANUAL_HANDOFF_CONTRACT.md](GOAL_MANUAL_HANDOFF_CONTRACT.md). The Stage 7C.2B.3 checkpoint remains an implementation candidate until independently reviewed. The desktop handoff surface and external-attestation design are not included; 7C.2B.4 and 7C.3 have not begun.

## Stage 7C.2B.5A external-integration attestation design — evidence candidate

The source audit found that `evaluateCompletion()` currently accepts an approved user `final_apply` approval with `action: "applied_externally"` when its detail matches only the current definition version/hash and Goal integration head. It does not require a handoff, registered repository identity, destination ref, observed destination commit/tree, or Git-verification evidence. `checkCompletionProof()` binds the proof to the current Goal definition and integration head; it does not re-read the base branch. This existing v1 behavior is not rewritten by the design stage.

The new design proposes a distinct v2 external-integration action and immutable attestation linked to the existing approval ledger and exact immutable handoff. A strict v2 completion policy would require both an explicit user decision and read-only proof that the exact handoff source commit and expected base commit are ancestors of the exact recorded base ref's observed commit. That proves source-history inclusion at an observation time; it does not prove conflict-resolved tree equality, clean worktree state, or permanent ref currentness. Squash, rebase, cherry-pick, patch similarity, tree equality without ancestry, and assertion-only evidence do not meet the proposed strict v2 threshold.

Important compatibility finding: `validateManualHandoff()` treats the destination's expected base commit as part of currentness, so a successful external integration makes an ordinary handoff projection stale. A future attestation-specific verifier must validate immutable handoff authority separately and accept only the proven expected-base/source ancestry transition; it must not weaken ordinary handoff staleness or treat every `base_diverged` state as success.

Deterministic characterization is in `src/server/goals/externalIntegrationCharacterization.test.ts`: 12 cases passed on Linux 6.8 / Git 2.43.0 / Node 22.23.1, including exact fast-forward/merge ancestry, squash/cherry-pick/rebase identity changes, partial and conflict-altered integration, wrong repository/ref, source-ref movement, same-tree unrelated target movement, a ref-movement barrier, a linked-worktree ref update, dirty checkout state, and SHA-1/SHA-256. This is Git-only evidence from disposable repositories, not production attestation or Windows qualification. Windows remains unverified.

The proposed v2 policy, record, recovery, compatibility and activation risks are in [GOAL_EXTERNAL_INTEGRATION_ATTESTATION_DESIGN.md](../history/goals/GOAL_EXTERNAL_INTEGRATION_ATTESTATION_DESIGN.md). No migration 026, endpoint, approval action, completion evaluator change, Goal transition, or production Git writer is implemented. `applyApprovedGoalToBase()` remains quarantined; production remains on `DisabledGoalExecutor`. This design checkpoint awaits independent review.

## Stage 7C.2B.5B — internal external-integration authority candidate

Migration 026 and `src/server/goals/externalIntegration.ts` now add a distinct version-2 `confirm_external_integration` approval digest, a read-only registered-repository ancestry observation, immutable attestation persistence, and fresh current/historical/stale/unavailable/invalid validation. The old `intent_digest`/`apply_to_base_intent` contract and its operation table are unchanged. The action requires a separate exact user-approved decision and cannot authorize a Turing integration operation.

The proof is explicitly `source_history_observed`, not content preservation. `git merge -s ours --no-ff` can satisfy source and base ancestry while omitting accepted files. The projection states `contentPreservation: not_proven` and `goalCompletion: not_completed_by_attestation`. The attestation table is not read by `evaluateCompletion()`; final apply remains unsatisfied and no completion proof or Goal transition is created.

This implementation candidate has no user-attestation endpoint, UI action, automatic approval, Git write, provider/model call, or subscription use. The observation and SQLite commit are not atomic; repeated reads detect only movement during the sampled interval. Windows remains unverified. See [GOAL_EXTERNAL_INTEGRATION_AUTHORITY_CONTRACT.md](GOAL_EXTERNAL_INTEGRATION_AUTHORITY_CONTRACT.md). The candidate awaits independent review; 7C.2B.5C/D and 7C.3 have not started.
