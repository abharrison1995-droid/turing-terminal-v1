# Goal Engine end-to-end acceptance matrix

Stage 7C.1 is accepted; Stage 7C.2A adds a bounded final-apply authority checkpoint pending independent review. The matrix distinguishes existing lower-level coverage from cross-component scenarios that have actually traversed the production authorities. `End-to-end fake-provider-proven` never means live-provider, physical-device, or release acceptance.

## Evidence levels

- **Unit-proven** — a focused module or policy test establishes the invariant.
- **Integration-proven** — multiple production modules or a real SQLite/Git/RunEngine boundary are exercised, but the complete Goal lifecycle is not.
- **End-to-end fake-provider-proven** — a bounded Goal lifecycle uses production supervisor, definition/approval authority, run launcher/engine, broker, Git integration, and evidence/completion paths with only external provider responses faked.
- **Physical/live pending** — real provider/account or physical-device evidence has not been supplied by this stage.

“Implementation status” describes 7C.1 work, not whether a feature exists in the product. The observed-results section below is authoritative; evidence levels remain limited to what each test actually exercises.

- **Route validation cost:** `routeProbe.test.ts` confirms a metered lane is not probed through route validation; no route validation purchase or provider request occurred in 7C.1.

### Required-category classification

- **Already implemented:** read-only `preflightFinalApply()` and GET preflight route; bounded preview/read-model `final_apply` next action; `goal_approvals` supports `final_apply` and user-only approval; `goal_integration_ops` supports an `apply_to_base` operation value; completion recognizes an applied operation at the current integration head or a user-approved `applied_externally` detail bound to the current definition version/hash and integration head.
- **Implemented in 7C.2A:** a strict versioned intent binds Goal/definition/source/destination/repository/review identities; `evaluateCompletion()` and `preflightFinalApply()` are both required; digest metadata is immutable and duplicate live intents are constrained by SQLite; stale pending approvals are refused and settled on a changed request; the generic user decision route revalidates before approving. The read-only validator is available for 7C.2B.
- **Existing but needs extension:** operation checks are immutable generic JSON, but no writer creates `apply_to_base` and recovery skips that op; current external attestation has no dedicated mutation route; preflight remains only a snapshot and must be recomputed at the write boundary.
- **Missing:** public request endpoint and UI action; fast-forward-only base-ref writer; durable operation association to exact target ref, source/target commits and approval; base-ref crash recovery. No such write occurred in 7C.2A.
- **Schema:** migration 023 covers only approval intent metadata; 7C.2B may need additional typed operation authority if immutable JSON cannot prove the full crash-recovery record.
- **Unresolved for 7C.2B:** operation retry/recovery behavior after an interrupted base-ref write; how external application records the observed base head and stays distinct from a Turing-owned operation; safe worktree/index synchronization after a successful ref update.

| Git scenario                        | Characterized result                                                                                                 | Strict v2 completion proposal                                                              |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Fast-forward                        | Expected base and exact Goal source are ancestors; tree equals source with no later changes                          | Eligible only with explicit user confirmation and exact repository/ref/handoff identity    |

| Unrelated target commits            | A merge that retains both histories preserves base/source ancestry; later unrelated commits also preserve ancestry   | Eligible at an observed ref tip if exact recorded destination and current identities match |
| Forced/unrelated target move        | Source/base ancestry can disappear                                                                                   | Refuse when observed                                                                       |
| Wrong repository or ref             | Identical Git commit IDs can exist in independent repositories; another branch may not contain source                | Refuse using registered repository and exact handoff destination identity                  |
| Moved source ref / outdated handoff | Old object can remain readable, but no longer matches handoff source identity                                        | Stale; refuse without retargeting                                                          |

The proposed policy is intentionally stricter than a user statement alone: only an explicit user decision plus read-only proof that the exact handoff source and expected base are ancestors of the exact recorded base ref may satisfy a new version-2 `applyToBase: "required"` contract. The proof is historical at `observedAt`; it does not promise the branch remains unchanged, the checkout is clean, or conflict-resolved content equals the reviewed tree. Assertion-only, tree-only, patch-similar, squash, rebase and cherry-pick outcomes remain manual reconciliation. Existing definition versions and legacy `applied_externally` approvals keep their original meaning and cannot be reused as v2 authority.

The existing handoff projection becomes stale when base integration moves the recorded base ref. Future implementation therefore needs a separate attestation verifier for immutable handoff authority and source/base ancestry; it must not weaken the existing stale state. Git observation and SQLite commit cannot be atomic, and a post-completion correction cannot rewrite a terminal Goal. Both limitations are explicit design gates.
