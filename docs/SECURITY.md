# Security and trust boundaries

## Local master

The Node service binds to `127.0.0.1` by default and rejects non-loopback `TT_HOST` values. Local loopback requests do not require a Turing device token and are trusted to the local user account. Loopback does not protect against another process running as that same user.

Remote browser requests must arrive through Tailscale Serve with its `Tailscale-User-Login` identity header, then present a desktop-approved device token in an `HttpOnly`, `Secure`, `SameSite=Strict` cookie. Pairing codes expire after five minutes and are stored only as SHA-256 hashes. QR URLs contain only the HTTPS Serve origin and a short-lived request UUID; the claim still requires Tailscale identity and desktop approval. Claims are single-use, can be explicitly denied, and expire with the request. Device tokens are stored as hashes, expire after 90 days, are bound to the normalized Tailscale login, and can be revoked from desktop Settings. The browser does not receive token material through JavaScript or local storage. Turing trusts the identity header because it remains bound to loopback; do not bind the service directly to a network interface. Tailscale identity is an additional boundary, not a replacement for Turing's device approval. Pairing does not support tagged Tailscale devices without a user identity, and end-to-end phone testing remains outstanding.

The health route returns only service/version/local-binding information without a device token. It permits cross-origin reads so a saved machine profile can verify that the target is a Turing master; it sends no credentials and exposes no project or run data. The service has no public-internet or Funnel support. Restrict access to the Tailscale Serve node to intended user-owned devices using tailnet ACLs. Tailscale Serve does not supply the user identity header for tagged devices; this pairing flow rejects connections without a user identity, and tagged/identity-less devices must not be granted access expecting Turing device approval to cover that case. The browser stores only machine URLs and display metadata in local storage. Profile transfer during a machine switch contains no device or provider tokens; the selected master still requires its own host-scoped approved cookie.

## Credentials and data

Provider CLIs keep their own sign-in state; Turing does not read provider credential stores. The only keys Turing stores are optional OpenRouter inference/management keys, entered on the desktop (paired phones receive 403 for credential and budget changes), kept in `<data dir>/secrets/credentials.json` outside SQLite with owner-only permissions, never returned by any API, and used only inside the server-side OpenRouter adapter. Provider, build, and test child processes remove environment variables whose names indicate tokens, secrets, passwords, API/access/private/management/provisioning keys, passphrases, credentials, or auth configuration, every `OPENROUTER_*` variable, and OpenAI/Anthropic base URLs. This name-based filtering is incomplete and cannot identify secrets stored under unrelated variable names. Run the local master with an appropriately scoped account and environment.

The SQLite database is stored in `~/.turing-terminal` by default. Turing attempts to set the data directory to mode `0700` and the database file to `0600` on platforms that support POSIX modes. Database contents include prompts, project paths, stage output, logs, review findings, approval decisions, and observed usage. Treat the data directory as sensitive and include it in local backup and deletion policies.

Provider output and process logs are persisted. Common token shapes such as `sk-…`, GitHub tokens, and bearer tokens are redacted from displayed output. Broker writes reject likely credentials, and protected credential paths are denied in every permission mode. This is pattern-based protection, not a complete secret detector. Do not submit secrets in prompts or project files. Reviewer diffs include tracked changes and safe, small untracked text files; environment files and common key/credential file names are excluded from untracked diffs.

Optional Web Push VAPID private keys remain in the local master environment and are never returned by the API. Subscription endpoints and browser key material are stored only in the private local database, redacted from request logs, and capped at 20 entries. The server accepts HTTPS endpoints only from known browser push-service domains to avoid turning notification delivery into arbitrary server-side requests. Push payloads are generic and do not include prompts, logs, error text, or credentials. Delivery still depends on the browser vendor's push relay.

## Commands and repository access

The user registers a project folder explicitly. Codex, OpenCode, and Claude Code receive no native shell or project-file tools; they can act through the per-run MCP broker, which checks canonical paths, symlinks, secret rules, role, and permission mode and records each operation. Cline uses its documented file-based tool-approval interface and Turing authorization callback; the CLI executes an approved action, so Turing cannot capture the action's individual stdout/stderr as it does for broker-executed operations. Use trusted repositories and a least-privilege operating-system account.

Git worktree isolation requires a clean Git working tree and starts from the current `HEAD`. It isolates the checkout, but is not an operating-system sandbox and does not prevent network access. When a folder is not a Git repository or isolation is turned off, stages run in the registered folder itself.

The four permission modes are enforced by the Turing broker: Supervised asks before mutations and commands; Normal permits routine project edits and configured build/test/lint scripts but asks for consequential operations; YOLO reduces routine approval friction while keeping remote, destructive, secret, and out-of-project boundaries; ENIGMA requires deliberate run confirmation and keeps the same hard secret/path/network/destructive protections. First-class Git stages use the same rules: Supervised and Normal ask before commits, YOLO and ENIGMA can commit, push always asks because it may use a Git credential helper, merge always asks, and rollback always asks. These are application-level action controls, not a full OS sandbox. Package scripts and allowed project processes still run with the local user's operating-system permissions. Turing-managed Git commit, push, and merge stages suppress repository hooks, and commit signing is disabled for those commits, to prevent those operations from launching unmediated local programs.

Git operations require an isolated worktree created from a clean starting repository. Commit, checkpoint, push, and merge verify that changed paths stay under the registered project folder. Commit and checkpoint also reject sensitive filenames and content matching known credential patterns; this detector is not exhaustive. Merge displays a redacted diff preview, checks that the original branch is unchanged and clean, and uses `--ff-only`. Push uses an explicit remote/refspec and never force-pushes. Rollback runs only after approval, resets the run branch to its start, restores the chosen tree inside the registered subtree, and removes only non-ignored untracked files created after the restore point. Ignored files remain for inspection. These safeguards do not contain arbitrary code that a repository's package scripts or Git hooks execute.

## Recovery

Run state and events persist in SQLite, including first-class Git operation and approval records. Closing the browser does not own or terminate the run; the local service continues it. If the service restarts while a run is active, the engine pauses that run; inspect its Git working tree before resuming or discarding work. A pending human approval is denied/reset for explicit review. Git changes are committed, pushed, or merged only when the workflow contains those stages; force-push is not implemented.

## Goal authority routes (GH.1), 2026-10-13

GH.1 (S1a) makes the server refuse paired remote devices on five user-only Goal authority routes. All five are `POST`:

- `/api/goals/:goalId/handoffs/:handoffId/external-integration/attestations/:attestationId/corrections`
- `/api/goals/:goalId/handoffs/:handoffId/external-integration/attest`
- `/api/goals/:goalId/completion-decision`
- `/api/goals/:goalId/completion`
- `/api/goals/:goalId/attestation-corrections/:approvalId/decision`

A refused request receives `403` with `{ "error": "Goal completion and correction can be changed on the desktop only.", "code": "desktop_required" }`. The check runs first in each handler, before the Goal lookup and body validation. The signal is the existing remote predicate, `isRemoteRequest` in `src/server/routes/requestIdentity.ts`, supplied to the Goal routes as `requireDesktopCaller`. A request is remote when it carries a Tailscale identity header, or when its Origin or Referer, or its Host, is not a loopback name, or when Host is missing. A request with no identity header and a loopback Host and Origin is local, whatever the client claims. User-Agent, viewport, `x-device-type`, `sec-ch-ua-mobile` and `x-forwarded-*` headers are not read for this decision. A paired device without a valid device cookie still receives the existing `401`. Local callers keep their current behaviour. The other Goal routes, including handoff preparation, goal-approval decisions, and pause, resume, start and abandon, are unchanged.

Residuals and open verification:

- A same-user local process on the desktop machine is not distinguished from the desktop UI. The owner conditionally accepted this residual for V1 on 2026-10-13 (O1), with live Tailscale identity-header and Host behaviour verification as its condition. O2, a verified process boundary, may be post-V1. See [GOAL_TRUSTED_CALLER_BOUNDARY.md](goals/GOAL_TRUSTED_CALLER_BOUNDARY.md).
- Live Tailscale Serve header behaviour, including whether `Tailscale-User-Login` can be stripped or injected and how Host is rewritten, is not verified by automated tests and remains pending physical acceptance. This is the condition on O1, not a waived gate. A remote request misclassified as local that reaches a desktop-only Goal route is a blocking defect.
- No physical-device, live-provider or accessibility result is established by this change.
