# Goal final-apply architecture decision — Stage 7C.2B.2

Status: design and disposable-repository characterization only. No replacement writer, migration, execution endpoint, or UI action is implemented. The checked-out-worktree writer from rejected Stage 7C.2B remains quarantined and production still uses `DisabledGoalExecutor`.

## Decision

**DECISION C — Manual handoff is the safe V1 boundary.** Turing should finish and verify Goal work, retain its existing Goal integration ref, and produce an immutable handoff record containing exact Git identities, bounded review material, verification/review evidence, and read-only inspection instructions. The user performs any checkout or integration through a deliberate Git operation they control.

The handoff is not a final application. For a Goal whose current policy says `applyToBase: "required"`, handoff alone must not make `finalApply.ok` true or complete the Goal. A distinct `ready_for_manual_integration` concept may report that the accepted result is prepared. Existing `applied_externally` remains a separate explicit user attestation and is not proof generated by Turing. This stage does not implement either concept or change `evaluateCompletion()`.

Approach A is rejected under the arbitrary-concurrent-Git-process threat model: an occupancy listing is a snapshot, and Git has no portable atomic operation that couples “this ref is not checked out in any worktree” with `update-ref` compare-and-swap. Approach B avoids moving the user’s base ref, but still mutates shared repository state and can race with an unborn linked worktree whose symbolic `HEAD` names the proposed delivery ref. It also duplicates the existing `refs/heads/turing/goal/<goal-id>` source ref without a demonstrated V1 need. Approach D is an attestation after the user acts, not an application mechanism or a handoff by itself.

This decision is not independent stage acceptance and does not qualify final apply for production. Stage 7C.3 has not started.

## Historical evidence and failure model

Stage 7C.2A, independently accepted at `3a69f33b6d8eda175736a93f0044324e86b07f6c`, introduced version-1 prospective authority for a future operation that updates the recorded base branch and synchronizes its registered checked-out worktree. That approval is valid only for that original contract. It does not authorize a different ref operation or a manual handoff.

Stage 7C.2B was rejected. Stage 7C.2B.1 was accepted only as a blocked evidence checkpoint, not as a successful remediation. The confirmed loss sequence was:

1. A valid prospective final-apply approval existed.
2. The source/destination Git CAS succeeded.
3. The final collision scan passed.
4. An ignored file was created after that scan.
5. `git read-tree -m -u` overwrote that file.
6. Git returned success.
7. The checkout appeared clean.
8. Completion was incorrectly satisfied.

The final collision scan cannot serialize arbitrary filesystem writers. More scans, shorter delays, Turing-local mutexes, filesystem watchers, post-operation status checks, and best-effort backups do not close this interval or recover bytes already overwritten. `read-tree` also has a characterized partial-update failure on a different path. The original implementation therefore cannot meet the stated user-data preservation guarantee.

## Git concurrency findings

The characterization suite uses disposable repositories and independent Git subprocesses. It does not call `applyApprovedGoalToBase()` and does not modify the user repository.

### Destination occupancy race

The test records `git worktree list --porcelain -z`, confirms `refs/heads/main` is not checked out, then creates a linked worktree on `main` before attempting the destination CAS. Git accepts low-level `git update-ref refs/heads/main <approved> <expected-old>` while that branch is checked out. The linked worktree’s symbolic `HEAD` resolves to the approved commit, but its index tree and tracked file bytes remain at the old base; the approved new file is absent. This directly disproves an atomic occupancy guarantee from a pre-CAS worktree listing.

In the same fixture, normal `git switch main` and `git checkout main` refuse when another worktree owns the branch. `git switch --ignore-other-worktrees main` can bypass that protection. `git branch -f main <commit>` refuses the checked-out branch, but `update-ref` succeeds. These higher-level command rules do not make the low-level CAS occupancy-aware.

The reverse ordering was also characterized: when CAS completes first, a later `git worktree add` materializes the new commit consistently in the new checkout. This proves only that one ordering is coherent; it does not reserve the interval in the opposite ordering.

### Linked worktree and delivery-ref race

`git worktree list --porcelain -z` reports linked worktrees and their branch registrations. When a linked-worktree directory is removed while its administrative record remains, the listing marks it `prunable` and continues to report its branch until explicit `git worktree prune`. A scan therefore must decide how to treat stale registrations, and pruning metadata is itself external repository state. Neither choice closes a race after the scan.

For Approach B, a disposable repository creates an orphan linked worktree with `git worktree add --orphan -b turing/delivery/<id>`. The worktree has a symbolic `HEAD` naming that branch, but no branch ref yet and an empty index. A create-only `update-ref` with an all-zero expected old object ID succeeds. That worktree’s `HEAD` then resolves to the new commit while its index remains empty and approved files are absent. The result ref is not the user base branch, but it is still shared repository state that external Git clients can observe and mutate around.

### Ref identity and transaction limits

The suite separately moves the approved source ref and the destination ref after reading their values. A `git update-ref --stdin` transaction containing `verify <source> <expected-source>` and `update <destination> <new> <expected-old>` rejects each stale case without overwriting the external movement. This is the useful guarantee: the named refs still had the exact expected object IDs at the transaction boundary, or the transaction failed.

It does **not** prove that a ref is unoccupied by a worktree, lock a checkout, coordinate the Git index, serialize arbitrary Git clients’ higher-level operations, or protect filesystem contents. A disposable test placed a lock file at the common-dir `refs/heads/main.lock`: `update-ref` refused while that exact ref lock existed, then succeeded after the lock was removed. Another test left the linked worktree's `index.lock` present and observed the common ref CAS succeed. This characterizes distinct ref and per-worktree index lock paths; it does not claim every checkout lock implementation is identical across Git versions/platforms. Git documents ref locking and compare-and-swap for the refs in the transaction; `git worktree` documents registrations and lock/prune behavior separately. A process-local mutex cannot coordinate another Turing process, CLI, or IDE.

Git references used for this distinction: [git-update-ref](https://git-scm.com/docs/git-update-ref), [git-worktree](https://git-scm.com/docs/git-worktree), [git-checkout](https://git-scm.com/docs/git-checkout), and [git-branch 2.43.0](https://git-scm.com/docs/git-branch/2.43.0.html). The tests characterize Git 2.43.0 on Linux; the docs do not establish cross-platform atomic occupancy.

## Ref namespace and operation contract

The repository already uses `refs/heads/turing/goal/<goal-id>` as the Goal integration branch. A separate `refs/heads/turing/delivery/<goal-id>` could be generated from a server-owned Goal identity, created with expected-old equal to the all-zero object ID, and recorded with source commit/tree, target base commit, repository identity, review digest, and reflog message. That would avoid overwriting an unrelated preexisting ref, but it would still be a new shared ref, could be named by an unborn worktree, and would not apply the result to the user’s required base branch. The existing Goal ref already identifies the verified source; no material V1 benefit justifies the additional mutable ref today.

If delivery is reconsidered later, it must be named **delivery**, not apply. It must have a new action discriminator/schema, exact repository and source identities, an explicit create-only/idempotency contract, no force update, no merge commit, no base-ref substitution, and completion semantics that say “delivery ref created,” never “applied.” This is not authorized or implemented here.

Approach C creates no Git operation. A future immutable handoff record should bind at least:

- schema version and `manual_integration_handoff` record discriminator;
- Goal ID, accepted definition version/hash, and final-acceptance identity;
- repository/project identity and Git object format;
- exact source ref, source commit and tree;
- exact target base ref and observed base commit/tree used for the reviewed diff;
- reviewed-change identity, complete changed-path digest, bounded diff/stat digests and truncation markers;
- evidence and independent-review identities;
- creation provenance and a canonical record digest.

Proposed record envelope: `{ kind: "turing_goal_manual_integration_handoff", schemaVersion: 1, ... }`. This handoff record is not an approval and cannot be parsed as `apply_to_base_intent`. The previously approved 7C.2A version-1 intent remains a record of approval for its original checked-out-base operation only. If Approach A were reconsidered, it would need a new `action: "update_base_ref_intent_v2"`, schema version 2, and an explicit base-ref-update mode. If Approach B were reconsidered, it would need a distinct `action: "create_delivery_ref_intent_v1"` and delivery mode. Neither is authorized by this decision. Any later external attestation should use its own versioned action (for example `attest_applied_externally_v1`) rather than reuse either Git-write intent.

## Completion contract

Keep the existing three decisions separate:

1. Final acceptance says the Goal output meets its accepted contract.
2. A prospective operation approval authorizes one exact Git operation; the v1 approval only describes the old checked-out-base operation and is not reusable.
3. An `applied_externally` attestation is an explicit user assertion that the user performed integration.

A fourth read-model concept, **ready for manual integration**, is useful to show that the accepted, verified source is prepared. It is not `finalApply.ok`, applied completion evidence, or Goal completion under the current `applyToBase: "required"` policy. `evaluateCompletion()` must stay strict. A future policy that treats handoff as a terminal deliverable would require an explicit new/versioned policy choice; it must not silently reinterpret `applyToBase: "required"`.

The current evaluator accepts Turing application only with its durable operation proof, and its generic `applied_externally` path requires a separate user approval detail bound to current Goal/definition and integration head. The latter is an assertion path, not a Turing writer. No external-attestation mutation is implemented in this stage. A delivery ref alone never proves the base was updated or a checkout was materialized.

## User-facing workflow and remaining user action

A future desktop presentation should distinguish **Ready for review**, **Approved**, **Ref updated**, **Awaiting manual integration**, **Applied externally**, and **Completed** according to actual evidence. Under this decision, a manual handoff should show:

- registered repository/project and canonical repository identity;
- exact source branch/ref, source commit and tree;
- exact target base ref and observed old commit/tree;
- bounded diff preview/stat and whether the display was truncated, plus review/evidence identities;
- a plain statement that Turing did not change a ref, `HEAD`, index or file and that the result is not yet applied;
- read-only commands or Git GUI navigation to inspect `git show <source-commit>` and `git diff <base-commit>..<source-commit>`.

The user then chooses whether and where to integrate. A user-controlled, separately created worktree can provide an isolated inspection area; Turing must not create or switch it automatically. Before any manual merge/fast-forward, the user should inspect repository identity and `git status`, retain or commit/stash their own changes, and review the exact source/base identities. If the base moved after the handoff, the displayed diff is stale and must be reviewed again. Normal Git commands can still interact with ignored files and concurrent filesystem writers, so user-controlled integration is a deliberate operation with ordinary Git risks, not a guarantee supplied by Turing. Turing's V1 guarantee is narrower and verifiable: preparing the handoff does not perform that operation.

To satisfy the current required-apply completion policy after integration, the user would still need a distinct explicit `applied_externally` attestation flow once one is implemented. That flow must be presented as the user's attestation, not as a Turing-observed application. No command is required to create the handoff; the user must perform the later Git integration and, if they want the Goal marked complete under the existing policy, provide the separate attestation.

## Recovery and idempotency proposal

There is no Git transaction to replay for Approach C. A future handoff record has monotonic states such as `prepared`, `published` (if a user-visible immutable artifact is persisted), `stale` (if the source/definition/review or expected base changed), and `superseded`. These mean record availability only; none means applied. Database recovery may re-read immutable row/digest and current read-only Git identities, but must not move refs, check out files, or infer external application.

If a future delivery-ref mode is separately approved, its durable operation should distinguish `planned`, `created`, `unknown_outcome`, `external_ref_movement`, and `stale`; recovery may observe refs/reflog only. It must not repeat CAS, rewrite a ref, checkout, merge, reset, or mark base application from delivery-ref existence. Create-only CAS with expected-old zero gives idempotency only when an existing ref’s exact commit and immutable operation provenance match; any other existing value is a collision/refusal.

The old v1 operation record and recovery proof retain their current interpretation and must never be used to recover a new mode.

Approach C removes Turing as a Git mutator in this stage, so concurrent Git processes cannot race a Turing branch update. It does not claim to make all later user operations safe from arbitrary filesystem writers. Linux experiments ran on Linux 6.8, Git 2.43.0, Node 22.23.1. Windows was not available; Windows behavior for worktree registration, locks, case handling, and checkout races is unverified. The decision does not claim cross-platform safety of ref updates. SHA-1 (40-character IDs) and SHA-256 (64-character IDs) ref/reflog behavior were characterized locally on Linux; Windows remains unverified.

Threat boundary by design:

- **A — base-ref update:** the protected assets are the approved destination ref and every worktree whose symbolic `HEAD` names it. The exact approval would authorize only a specific old/new ref pair, but an external CLI, IDE, another Turing process, user branch switch/commit/ref move, or linked-worktree add/prune can change occupancy after the scan. CAS protects exact source/destination object IDs, not checkout state. The demonstrated HEAD/index mismatch makes the residual risk unacceptable for V1.
- **B — delivery ref:** the protected assets are the Turing-owned result ref and any worktree naming it. A new mode-specific approval plus create-only CAS can protect against replacing an existing ref. It cannot see a worktree whose unborn symbolic `HEAD` already names that ref, and it does not prove a user base update. The observed empty-index/unborn-checkout mismatch and lack of product need make this unsuitable as final apply.
- **C — manual handoff:** Turing receives no Git-write authority. Another Turing process, CLI, IDE, user, or file watcher may change repository state while read-only identities/diffs are computed; the handoff must be refused or marked stale if the exact source/base/review snapshot changes. Once published, Turing has not changed the repo. A later user merge/checkout remains outside this guarantee and retains normal Git/filesystem risks. This narrower boundary is acceptable for V1 because Turing does not write a user ref or file.

For all designs, crashes, interrupted Git commands, database failure, and unreadable/corrupt repository state can make observations incomplete. A/B cannot recover an unproven checkout by replaying a ref update; C can leave the handoff unavailable or stale without changing completion. No file watcher, editor lock, or Turing mutex is accepted as a global-writer guard.

If a Git-ref mode is proposed again, its transaction contract must retain the exact approved source ref/commit/tree, destination ref and expected-old commit, fast-forward ancestry, full changed-path/sensitive-content scope checks, one atomic `update-ref --stdin` transaction verifying source and destination CAS, no force/no merge commit, and an operation-unique reflog message. That transaction proves only ref identity and ref movement. It does not prove occupancy, checkout/index synchronization, or user-file safety. A delivery-ref creation must use expected-old equal to the repository-format-specific all-zero object ID and treat any existing ref as collision unless immutable operation evidence proves an identical idempotent result.
