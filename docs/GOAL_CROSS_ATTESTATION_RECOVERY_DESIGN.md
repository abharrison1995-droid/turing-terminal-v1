# D.4R Slice 0 design: Cross-Attestation Completion Recovery

Status: read-only reconciliation at HEAD b233312. Nothing was run, edited or staged. No acceptance evidence is claimed; every
statement below is a source reading with file:line. Paths are under `src/server/goals/` unless prefixed.

## 0. Verdict in one paragraph

No migration is needed. The schema permits any number of completion approvals per Goal (only identical digests collide), exactly
one proof per Goal, and a correction chain of at most two entries that can only grow. Every cross-decision rule the owner policy
needs is a read over existing rows, enforceable inside the existing `BEGIN IMMEDIATE` transactions. The one genuine design
constraint is that the 20-key completion-action trigger (migration 027:20-36) forbids adding a field to the stored decision, so
any binding of the policy state must ride on existing fields (`userReviewedPreflightDigest`) or on the in-memory `SnapshotIdentity`.

**Does anything prevent two live decisions (A and B) for one Goal?** No. Nothing at the schema level; nothing in code
(`classifyCompletionRows` skips other attestations, 194). **Is a schema change needed?** No.

Justification that code-only is enforceable: (1) the only writer of completion approvals is `recordLocked`'s immediate txn; (2) in that
txn the classifier reads every completion row and every relevant correction chain; (3) SQLite has a single writer, so read-then-write
inside `BEGIN IMMEDIATE` is atomic against any other connection, including correction appends; (4) because ineligibility is monotone,
a decision recorded when all others were ineligible can never later face an eligible competitor except through another decision, which
the same classifier would refuse. A trigger could duplicate (3) but would require migration 029 and cannot read Git-free chain
verification (digests) anyway. The proposed trigger would only catch the case where code is bypassed, which the static guard
(`goalAuthorityStaticGuard.test.ts:77-191`) already makes a test failure. **Recommendation: no migration.** If the lead later wants
defence in depth, the narrowest candidate would be a BEFORE UPDATE trigger on `goal_approvals` (pending->approved, completion digest not
null) aborting when another approved completion approval exists whose attestation has no row in `goal_attestation_corrections`; it is NOT
recommended because the chain-validity part (class 5) cannot be expressed in SQL.

## 4. Classifier design

Module: new leaf `completionAuthorityPolicy.ts`, DB-only, no Git, no writes, no clock. Entry point
`classifyCompletionAuthority(db, goalId, selectedAttestationId): CompletionAuthorityClassification`.

### 4.1 Inputs it reads (all existing rows)

1. `goal_external_completion_proofs` rows for the Goal (count and ids).
2. Every completion row: `completionRows` + `validateCompletionApproval` (decision.ts:109-145). Today these live in `externalCompletionDecision.ts`,
   which imports the preflight; the preflight cannot import it back (cycle) and the static guard `preflight_isolation`
   (`goalAuthorityStaticGuard.test.ts:183-190`, plus the identifier scan at `externalCompletionPreflight.test.ts:814-845`) forbids the
   preflight from naming `externalCompletionDecision`, `listExternalCompletionDecisions`, `readExternalCompletionDecision`. So Slice 1 extracts
   the read-only functions to a leaf `externalCompletionDecisionRows.ts` (pure move; `externalCompletionDecision.ts` re-exports so existing
   importers and the `decision_reader` rule are unaffected) and the classifier is a third module the preflight may import.
3. For each valid decision, its attestation's immutable record (`loadValidatedRecord`) and correction projection (`getAttestationCorrectionStanding`).

### 4.2 Per-decision entry

For each completion row R with parsed action `a`:

- `decisionId = R.id`, `actionDigest = a.actionDigest`, `reviewedPreflightDigest = a.userReviewedPreflightDigest`
- `attestationId = a.attestation.id`, `attestationRecordDigest = a.attestation.recordDigest`
- `integrity` = `ok` iff ALL hold (else the whole Goal is class 5):
  - row valid per `validateCompletionApproval` (shape, digest equality, approved by user, no foreign digests)
  - `a.goalId === goalId`
  - `loadValidatedRecord(db, goalId, attestationId)` returns a record (a missing/invalid attestation, including D17b's fabricated UUID, is NOT ok)
  - `record.recordDigest === a.attestation.recordDigest`, `record.actionDigest === a.attestation.actionDigest`, `record.approvalId === a.attestation.approvalId`, `record.handoff.{id,digest} === a.handoff`
  - `a.correctionChain.attestationId === attestationId`, `a.correctionChain.sequence === 0`, and `a.correctionChain.digest === computeEmptyCorrectionChainIdentity({attestationId, attestationRecordDigest}).digest` (preflight.ts:236-256)
  - `getAttestationCorrectionStanding` does not throw AND `standing !== 'invalid'`
- `correctionStanding`, `correctionSequence` (`tip.sequence` or 0), `correctionTipDigest` (`tip.correctionDigest` or null), `correctionCount`.
- `eligible` = `correctionStanding === 'active_uncontested' && correctionCount === 0 && tip === null` (the exact predicate at
  preflight.ts:457-462). Ineligible kinds: any non-empty verified chain, i.e. tip kind `dispute` (standing `disputed`), `withdraw`
  (`withdrawn`) or `supersede` (`superseded`), and for `[dispute,withdraw]` / `[dispute,supersede]` the standing is the tip's.
  `eligible` deliberately does NOT mean "would pass a Git preflight right now" (see ambiguity A1).

### 4.4 Canonical classification identity (`policy identity`)

```
entries = sort-by-decisionId( for each completion row:
  { decisionId, actionDigest, reviewedPreflightDigest, attestationId, attestationRecordDigest,
    integrity: 'ok' | <invalid reason>, standing, correctionCount, correctionSequence,
    correctionTipDigest|null, eligible } )
body = { schemaVersion: 1, goalId, selectedAttestationId, class, proofRows: P.length, proofIds: sort(P.ids), entries }
policyDigest = sha256( 'turing-goal-external-completion-policy-v1' \0 canonicalJson(body) )
```

Domain-separated like the existing digests (`externalCompletionPreflight.ts:226-228`). Derived entirely from existing rows; **no new column**.

### 4.5 Binding the same policy state across preflight, decision and completion

1. **SnapshotIdentity** (`externalCompletionPreflight.ts:330-341`) gains two keys appended AT THE END (so `firstDifference` keeps naming `handoff_fingerprint` etc. first, preserving the pinned details at `externalCompletionPreflightSeams.test.ts:223`, `externalCompletionDecisionSeams.test.ts:97`, `externalCompletionTerminal.test.ts:625`): `policy_class: string`, `policy_digest: string`. Keep `proof_rows` and `completion_approval_rows`. Captured in `readSnapshot` (pre-Git, post-Git, decision txn, terminal txn) so:
   - Preflight: pre-Git == post-Git or `observation_changed` (case 13).
   - Decision txn: `firstDifference(reviewed, current)` already runs at `externalCompletionDecision.ts:312`; the new keys make a competing decision or any correction on ANY decided attestation between review and commit an `authority_changed_during_decision` (cases 12, 15).
   - Completion: the post-Git identity is compared in the terminal txn (`externalCompletionTerminal.ts:155-163`); the same keys apply.
   - Own-entry inclusion: the digest includes B's own decision entry. That is correct for the in-memory identity because the flows compare identities captured after B's decision exists (completion) or tolerate the pre-commit/post-commit difference through the existing "exact reuse before compare" ordering (decision.ts:273-300).
2. **Persisted binding** (optional, recommended small): the stored decision cannot gain a field (027:20-36), but it already stores `userReviewedPreflightDigest`. Add an OPTIONAL fact to the report `facts` (`externalCompletionPreflight.ts:121-141`), e.g. `priorDecisionPolicy: { class: 'corrected_only', digest }`, **present only for class 3 and computed over `oth` entries only** (excluding the selected attestation's own entry, otherwise the digest would differ between the pre-decision review and the post-decision completion preflight, which `externalCompletion.ts:218` compares). Omitted for class 1 (and class 2 reports derive from the same omission rule), so every existing golden digest (`externalCompletionPreflight.test.ts:715-790`) is unchanged and `PreflightObservationSummary` untouched. Effect: a B decision reviewed while A was corrected carries that fact into its proof, and a later change in `oth` eligibility entries (not a mere dispute->withdraw, because `eligible` is the only bit digested for `oth` here, not the tip) forces `reviewed_preflight_changed`. If the lead prefers zero risk to goldens, drop this item; the in-memory identity alone satisfies the owner policy, and the audit order is still derivable from timestamps (A's correction `decided_at` <= its append commit < B's decision `responded_at`).

## 6. Ambiguities and recommended resolutions

- **A1. "Eligible A" with a stale/Git-moved A.** Today's pinned T11 shows X stale and uncorrected, yet Y is recordable. Recommendation: eligibility is correction-standing only (DB-only, deterministic, matches owner wording "verifiably disputed, withdrawn or superseded"). A stale-but-uncorrected A therefore blocks B until the user corrects A. Reason: a Git-based eligibility would put Git inside a read transaction and make classification time-dependent. Cost: users must dispute/withdraw/supersede A first; UI copy must say so (Slice 3). Because B always has a later tip than A (section 3), this is the normal path, not a corner. OWNER CONFIRMATION RECOMMENDED because it flips two pinned tests.
- **A2. Superseded A.** Ineligible the moment the supersede is appended, whether or not the replacement R is decided. R gets no authority from supersession (`attestationCorrection.ts:172-185` only validates R's integrity). The user may pick any independently eligible B, not necessarily R. Case 3 asserts no decision for B is created or inherited.
- **A3. Withdrawn then reinstated.** Does not exist (028:167-178, `attestationCorrection.ts:157`). `[dispute,withdraw]` is final. No reinstatement logic. A future migration adding one must bump the policy schema version.
- **A4. Correction on B after B's decision, before completion.** B's decision row stays immutable and valid; B becomes ineligible. Completion refuses at fresh preflight (`attestation_disputed`, preflight.ts:451-456) and, if the correction commits after Git, at the terminal txn (identity mismatch `correction_standing`, terminal.ts:155-163). Classifier shows B as an ineligible historical entry. User may then select C (case 16). No extra write.
- **A5. Unknown-outcome read of B must show A's eligibility.** Yes. `GET /completion` must list every valid decision with `eligibility` and `correctionStanding` (additive field on `GoalExternalCompletionDecisionView`, `src/shared/goalApi.ts:861-868`). The D.4E read-first recovery uses only that GET (client `completionModel.ts:54-67`, `GoalCompletion.tsx:38-55`), so it needs no new write path.
- **A6. `state: 'decided'` with only ineligible decisions.** `externalCompletionApi.ts:88-89` returns `decided` for any valid decision, which would show "Your completion decision is recorded" for a void decision. Recommend `decided` only if at least one valid decision is eligible; otherwise `not_completed`. Keep the enum.
- **A7. Pending correction request on A.** A pending (undecided) correction approval does not make A ineligible; only an appended correction does (`attestationCorrection.ts:559`). Otherwise authority would hinge on an unreviewed request.
- **A8. Unreadable/invalid historical decision or chain (class 5).** Permanently refuses all new decisions; no repair path exists in the product. This is the owner's "fail closed". Recorded as an accepted limitation, the same as today's D18 (decision.test.ts:902).
- **A9. Pending or denied completion approvals.** `validateCompletionApproval` marks them invalid (`approval_fields_invalid`, decision.ts:131-143), hence class 5. Unreachable through production paths because request+decide share one savepoint (276-294) and the generic route refuses pending completion approvals (goalCommands.ts:161-170).
- **A10. Explicit selection vs auto-select.** `GoalExternalIntegration.tsx:353-354` auto-selects `status.attestations[0]` when none is selected and mounts the completion panel for it (1142-1152). After A is superseded by a newer B, a remount would silently land on B. The panel's preflight GET is read-only, but "never silently select a replacement" suggests Slice 3 separates "viewing" from "selected for completion" (an explicit click before the Record control is available). OWNER CONFIRMATION RECOMMENDED because it changes D.4B behaviour.
- **A11. Report-body fact vs identity-only binding (section 4.5 item 2).** Recommend including the optional class-3 fact; fall back to identity-only if the lead wants zero golden risk.
- **A12. Which error code for class 4/5.** Recommend: preflight class 4 reuses `completion_already_recorded` with detail `competing_decision` (keeps `externalCompletionApi.test.ts:1022` and `unknownOutcomeRecovery.test.ts:597-600` assertions about the code valid); class 5 adds `completion_history_invalid`; the decision service adds `competing_decision` (409) beside `decision_conflict` (the existing message says "for this attestation", `externalCompletionDecision.ts:55`). New codes force entries in `EXTERNAL_COMPLETION_STATUS` (`goalRoutes.ts:242-270`, compile-time) and client copy (`completionModel.ts:100-127, 241-295`).
- **A13. Multiple stored decisions for one attestation.** Unchanged: same digest reuse, different digest `decision_conflict`; terminal requires exactly one (`terminal.ts:200`).
- **A14. Cost bound.** Classification reads one verified chain per decision. Decisions are bounded by attestations, which the UI already caps at 20 (`GoalExternalIntegration` status limit). Recommend a hard cap (e.g. 50 rows) that fails closed as class 5 `too_many_decisions`, with a test.
- **A15. Goal not `running`.** Check 2 (`preflight.ts:371-374`) precedes check 4, so classification only matters for running Goals. Class 6 on a `completed` Goal is therefore reported as `goal_not_running`; class 6 text only appears for an inconsistent running Goal.
